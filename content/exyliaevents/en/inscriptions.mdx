Sign-ups — *inscriptions* in the commands — restrict one configuration to a named list of players.
It is how a scheduled tournament stays limited to the people who signed up.

## The commands

All of them need `exyliaevents.admin.inscriptions`, which is separate from plain
`exyliaevents.admin`.

| Command | What it does |
|---|---|
| `/eventsadmin inscriptions open <configId>` | Opens the list for that configuration. |
| `/eventsadmin inscriptions close <configId>` | Closes it. |
| `/eventsadmin inscriptions add <configId> <player>` | Adds a player, online or not. |
| `/eventsadmin inscriptions remove <configId> <player>` | Removes one. |
| `/eventsadmin inscriptions clear <configId>` | Empties the list. |
| `/eventsadmin inscriptions startevent <configId>` | Starts the event with the list in force. |

The same is done from **Inscriptions** on the configuration's setup screen, behind the same node: open
or close the list, browse, add and remove players, clear it after a confirmation, and start the event.

## What "open" changes

While a configuration's list is **open**, only players on it may join that event. Anyone else is
refused with the `not-inscribed` message from `messages.yml`, whether they used `/events join` or the
menu.

Closing the list lifts the restriction: the configuration goes back to being open to everyone. The
list itself is not deleted by closing, so it can be reopened for a second round.

## A typical flow

<Steps>
  <Step title="Open the list">
    `/eventsadmin inscriptions open tournament1`
  </Step>
  <Step title="Collect names">
    Staff run `add` for each player. Offline players work — the list stores UUIDs, so somebody can be
    signed up days before.
  </Step>
  <Step title="Start it">
    `/eventsadmin inscriptions startevent tournament1` starts the event with the list applied.
  </Step>
  <Step title="Afterwards">
    `clear` before the next round, or `close` to open the configuration to everyone again.
  </Step>
</Steps>

<Callout type="tip" title="It pairs with scheduled events">
Open the list during the week, schedule the event for Friday in
[`scheduled-events.yml`](/docs/exyliaevents/game-flow#scheduled-events), and the event starts on its
own with only the signed-up players able to enter.
</Callout>

## Where it is stored

One row per configuration in `event_inscriptions`: whether the list is open, and the players on it.
Sign-ups survive restarts, and on a shared database they are visible to every server reading it.

## Access rules

Sign-ups are one half of a wider set of rules about who may join. Each configuration also keeps a
**blacklist** (players kept out), a list of **blocked ranks** (permission groups kept out) and a
**private** switch. The sign-up list is its **whitelist**: a private event admits only whitelisted
players. Opening a list with `inscriptions open` is the same as making the event private.

Every join path obeys the same order: a blacklisted player is always refused; a whitelisted player is
let in, even from a blocked rank; then blocked ranks are refused; then a private event refuses anyone
not whitelisted. Adding a player to one list takes them off the other. Ranks are read from your
permissions plugin through ExyliaLib's group lookup.

Each list exists per configuration and once globally, applied to every event. Use `global` as the
scope for the global one.

| Command | What it does |
|---|---|
| `/eventsadmin access` | Opens the global access screen. |
| `/eventsadmin access <configId\|global>` | Opens that configuration's access screen. |
| `/eventsadmin access <scope> public` / `private` | Turns the private mode off or on. |
| `/eventsadmin access <scope> whitelist add\|remove <player>` | Edits the whitelist. |
| `/eventsadmin access <scope> blacklist add\|remove <player>` | Edits the blacklist. |
| `/eventsadmin access <scope> rank add\|remove <rank>` | Edits the blocked ranks. |

They need `exyliaevents.admin.inscriptions`. Removals run at once; emptying a whole list is left to the
access screens, which ask first. The same screens open from **Access** on the configuration's setup
screen, and from **Global access** on the admin panel. A refused player is told which rule stopped them.

Plugins can ask the same question with `EventsAPI.canAccess(player, configId)`.
