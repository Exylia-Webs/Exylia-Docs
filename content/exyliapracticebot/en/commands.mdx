There are two roots. `/bot` is for players: typed on its own it opens the main menu, and its
subcommands act on your own bot. `/botadmin` is for staff and holds everything that needs
`exyliapracticebot.admin`. There are no other aliases.

Every player subcommand but `remove` needs `exyliapracticebot.use`, and the ones that spawn or
teleport also check their own feature node. Removing your bot never needs a node. See
[Permissions](/docs/exyliapracticebot/permissions).

## Player commands

Everything here has to be typed by a player: each one works on the bot that belongs to whoever typed
it, so the console has nothing to act on.

| Command | Permission | What it does |
|---|---|---|
| `/bot` | `exyliapracticebot.use` | Opens the main menu. |
| `/bot spawn` | `exyliapracticebot.use` + `exyliapracticebot.spawn` | Spawns your bot with your saved settings, one block above where you are standing. |
| `/bot remove` | — | Removes your bot. |
| `/bot tpme` | `exyliapracticebot.use` + `exyliapracticebot.teleport` | Brings the bot to you. |
| `/bot tpto` | `exyliapracticebot.use` + `exyliapracticebot.teleport` | Sends you to the bot. |
| `/bot reset` | `exyliapracticebot.use` | Puts every one of your settings back to its default. |

`/bot reset` also updates a bot that is already out: the new settings are pushed to it rather than
waiting for the next spawn. The reset row is saved to the database straight away.

`/bot tpme` and `/bot tpto` are asynchronous teleports — the confirmation arrives once the teleport has
actually happened, not when the command is typed. `/bot tpto` only goes to a bot you can see, in your
own world: the bot pearls and walks where a player cannot, and following it blind would carry you
through walls into closed areas.

Spawning and removing wait two seconds between uses, and the teleports one second; a use inside that
window is ignored without a message.

<Callout type="note" title="The menu does the same things">
`spawn`, `remove`, `tpme`, `tpto` and `reset` all have a button on the main menu, wired to the same
code; the menu's reset button asks for confirmation first, `/bot reset` does not. The commands exist so none of it depends on a menu file staying as it shipped. See
[Menus](/docs/exyliapracticebot/menus).
</Callout>

### What each refusal says

The lines below are the defaults from `messages.yml`; every one of them is editable, and each ships
with a sound and, in one case, a particle. The key is what matters — the text is yours.

| Refused | Key | Default line |
|---|---|---|
| Spawning in a world that is not in `worlds` | `bot.world-not-allowed` | *You can't spawn a bot in this world. Please use /rtp first* |
| Spawning when you already have one | `bot.already-has-bot` | *You already have a bot. Use /bot remove first.* |
| Spawning when the server is at its bot ceiling | `bot.limit-reached` | *The server is already running `%limit%` bots. Try again in a moment.* |
| `remove`, `tpme` or `tpto` with no bot out | `bot.no-bot` | *You don't have an active bot.* |
| `tpto` with the bot out of sight or in another world | `bot.bot-out-of-sight` | *Your bot must be in sight to teleport to it.* |
| Spawning or teleporting without the feature node | `bot.no-permission` | *You don't have permission to do that.* |

`%limit%` is the ceiling that refused the spawn — for a player, `max-bots` minus
`reserved-for-matches` — not a count of who is using them. See
[Limits](/docs/exyliapracticebot/limits).

A successful spawn answers with `bot.spawned`, a removal with `bot.removed`, the two teleports with
`bot.teleported-bot-to-you` and `bot.teleported-to-bot`, and a reset with `bot.settings-reset`.

## Admin commands

Everything here needs `exyliapracticebot.admin` and runs from the console as well as in game, except
`/botadmin settings`, which opens a menu and so needs a player. `reload`, `export` and `import` still
answer to their old spelling, `/bot reload`, `/bot export` and `/bot import`, so existing scripts keep
working; `settings` exists only under `/botadmin`.

| Command | Permission | What it does |
|---|---|---|
| `/botadmin reload` | `exyliapracticebot.admin` | Reloads the plugin's files. |
| `/botadmin settings` | `exyliapracticebot.admin` | Opens the settings hub: the values worth tuning in game. Player only. |
| `/botadmin export` | `exyliapracticebot.admin` | Writes every table the plugin owns into one dump file. |
| `/botadmin import <filename>` | `exyliapracticebot.admin` | Reads a dump back in. |

### Reload

Two named steps. `configs` re-reads `config.yml` and `messages.yml` and re-applies the message prefix;
`menus` compiles every menu file again. The menus step also runs on its own when ExyliaLib itself is
reloaded, so a menu edit picked up by an ExyliaLib reload does not need a second command here.

Reload does not touch player data — that lives in the database and is already what the plugin holds in
memory — and it does not remove bots that are out. A bot keeps running with the settings it was given.

### Settings

`/botadmin settings` opens a hub with three cards: **Defaults** (the starting mode, difficulty and
language), **Spawning** (the bot cap, the match reserve and respawn) and **Fighting** (the combat
values). Each card opens a page of hand-written settings that say what the value does, show the current
value and its default, and edit it on click. Only the settings an admin tunes while running the server
are there; everything else stays in `config.yml`, the same file you edit by hand, so either way works. See [Configuration](/docs/exyliapracticebot/configuration).

### Wiping player data

There is no wipe or reset command here. The plugin's one table, `practicebot_players`, is classified
for ExyliaLib as account data, so `/exylialib wipe ExyliaPracticeBotV3 <table|*> [code]` empties it
and `/exylialib resetplayer <player> [plugin|all] [@kind ...] [code]` clears one player's saved bot
settings. Both ask for a typed code before anything is deleted. See the
[ExyliaLib commands](/docs/exylialib/commands). A player resetting only their own settings uses
`/bot reset`.

### Export and import

Both go through ExyliaLib's transfer module, both run on a background thread, and both answer with a
report line when they finish: green when the transfer succeeded, red when it did not, and the line
itself names the outcome, how many tables, how many rows and how long it took.

`export` writes into `dumps/` inside the plugin's own data folder, creating it if it is not there. The
file is named for the plugin, the database engine and the moment it was taken —
`ExyliaPracticeBotV3-<engine>-<yyyyMMdd-HHmmss>.exyliadump.gz` — so two exports never overwrite each
other.

`import` takes exactly one argument: the **name of a file inside that same `dumps/` folder**, extension
included, as export wrote it.

```text
/botadmin export
/botadmin import ExyliaPracticeBotV3-h2-20260906-141355.exyliadump.gz
```

It is a name, not a path you choose: whatever you type is resolved under `dumps/`, so a dump copied
from another server has to be dropped in there first. Being a single argument, it also cannot contain
spaces — which the generated names never do.

<Callout type="warning" title="Import refuses to write over rows that already exist">
The import runs without the transfer module's force flag. If the table it is importing into already
holds rows, nothing is written and the report says which table and how many rows stopped it. That is
the safe half of the module on purpose: use it to move a database, not to merge two.
</Callout>
