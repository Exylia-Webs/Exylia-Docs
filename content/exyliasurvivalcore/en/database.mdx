---
title: "Database"
description: "The seventy-two tables, which module owns each, what they hold, and the schema quirks worth knowing."
---

Every module that stores anything opens its own tables, and a module that is off creates none. All of
them go through one connection, configured in `database.yml`.

Tables are created from the record definitions with `CREATE TABLE IF NOT EXISTS`, the first time each
repository is opened. There is no schema file to apply and no migration to run.

## Movement

| Table | Key | Holds |
|---|---|---|
| `spawn_data` | `id` | The spawn location. One row |
| `homes` | `id` = a UUID | The owner (indexed), name, location and icon |
| `sc_warps` | `id` | Display name, enabled, cost, permission, icon, location |
| `sc_warp_cooldowns` | `<playerUuid>:<warpId>` | When the player last used that warp |
| `tpa_settings` | `playeruuid` | Whether they accept requests, auto-accept and confirm |
| `rtp_cooldowns` | `id` | Player (indexed), world, when it was used |
| `sc_back` | the player UUID | Where they last left from, and when |

`/back` and the warp cooldowns are rows rather than memory because a warp can put the player on another
server, and the server they arrive on has to know both.

## Combat

| Table | Key | Holds |
|---|---|---|
| `player_stats` | `playeruuid` | Name, kills, deaths, best kill streak |
| `stat_cache` | `<uuid>:<statId>` | One cached stat value per player, for the leaderboards |
| `sc_stat_counters` | `<uuid>:<key>` | Every counter a module keeps: player name, counter key, amount |
| `sc_bounties` | `id` | Target, placer, amount, when it was placed, when it expires, anonymous |
| `sc_graves` | `id` | Owner, killer, location, the block the grave replaced, the items, the experience, when it expires and until when it is protected |

`player_stats` carries three descending indexes — on kills, deaths and best streak — so a leaderboard is
a bounded read. `sc_stat_counters` is what a `COUNTER` stat in `stats.yml`, a mission and a season all
read, so counting something new never needs a table of its own.

A grave's items live in its row and nowhere else: collecting it deletes the row, and only the collection
whose delete removed something pays out.

## Economy

| Table | Key | Holds |
|---|---|---|
| `sc_currencies` | `id` | One currency as set up in game: kind, order, names, symbol, icon, decimals, formats, aliases, item, starting and maximum balance, permission, transfer and exchange rules, leaderboard, networked, commands |
| `sc_economy_settings` | one row | Experience as a currency, the currency published to Vault and whether it is forced, whether the ledger is on |
| `exylia_balances` | `<uuid>\|<currency>` | One player's balance in one stored currency: player, name, currency, amount |
| `exylia_balance_pending` | a generated number | A change another server could not apply itself: player, currency, amount, whether it replaces the balance, reason, who made it |
| `exylia_ledger` | a generated number | Every stored operation: player, currency, change, the balance after it, reason, who made it, server, when |
| `sc_boosters` | `id` | Owner (empty for a global booster), type, source, multiplier, duration, when it expires (`0` while not started), who granted it |

An empty `sc_economy_settings` is a server whose currencies have not been set up yet. A balance row is
written only by the server its player is on; every other server leaves a pending row, which that server
folds in and deletes. See [Economy](/docs/exyliasurvivalcore/economy).

## Trade and vaults

| Table | Key | Holds |
|---|---|---|

## Modules that store nothing

`blocked-items`, `death`, `enchantments`, `kill-rewards`, `near`, `optimization`, `repair`,
`scheduled-commands`, `sell-wands` and `trade`. Kill streaks are counted in memory and lost on a restart.

## Things worth knowing before you touch a table by hand

<Callout type="note" title="A stored location can name another server">
Homes, warps, portals and crate blocks store `server,world,x,y,z,yaw,pitch`, where `-` means "this
server". That is what makes `/home` and `/warp` work across a network. A row naming a server that is
not this one has no local location at all — which is why the API offers a teleport method rather than
coordinates.
</Callout>

<Callout type="warning" title="Two tables have both `createdat` and `created_at`">
`sc_bounties` and `sc_loot_chest_templates` each carry two timestamp columns differing only by an
underscore, holding different things: the domain timestamp — when the bounty was placed, when the
template was made — and the row's own creation time. Read the right one.
</Callout>

<Callout type="danger" title="Some rows are claimed by deleting them">
A vote is paid, a season is closed, a vote party is started, a grave is collected, a protection is bought
or rented, and an order or a protection account is changed by whichever server manages to **delete** the
row first — only one delete succeeds, which is what makes each of those happen once across a network.
Deleting such a row by hand is not a clean-up: it pays nothing, closes nothing, or destroys what the row
held — and a deleted `sc_order_locks` row leaves its order unchangeable until the next start writes the
lock again.
</Callout>

The tables the plugin has had the longest also carry `created_at` and `updated_at`; the newer ones carry
only the columns above. Nothing has a unique constraint beyond its primary key.

## Sharing across servers

Point every server at the same database and homes, warps, kits, ranks, statistics, crates, balances,
protections and the rest are shared.
