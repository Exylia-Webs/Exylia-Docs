## Plugin nodes

| Permission | Default | What it gates |
|---|---|---|
| `exyliaprotections.use` | everyone | `/protections` and every subcommand outside `admin`, and with them the menus they open. |
| `exyliaprotections.select` | everyone | Protecting land by selecting two corners, when `selection.enabled` is on (off by default). Without it the hub hides the option. |
| `exyliaprotections.admin` | operators | `/protectionsadmin`, the old `admin` subcommands, the admin menus and every action in them. On every protection it also counts as the owner and as holding every role permission. |
| `exyliaprotections.bypass` | nobody | Building, using and entering anything inside any protection. |
| `exyliaprotections.bypass.warmup` | operators | Teleporting home, to warps and to plots at once, with no countdown and no cooldown. The node is `teleport.bypass-permission`; blank turns the bypass off. |

`exyliaprotections.bypass.warmup` is declared in the plugin's own `plugin.yml` but not in the loader's, which is
the one the server reads. A node nobody declares also defaults to operators, so it behaves the same.

`exyliaprotections.use` gates commands only. Placing a core a player already holds needs nothing but the
tier's own permission, when the tier names one.

## What admin lets through

`exyliaprotections.admin` is a management node, not a building one:

- Every subcommand and menu button that asks for **Owner** or a role permission passes: selling,
  transferring, upgrading, banking, editing members, roles and flags of anybody's protection.
- Entering is always allowed, whatever the protection's lock or bans say.
- A player holding it cannot be banned from a protection, and may edit their own entry in a member list.
- It does **not** let the player break, place or open anything in someone else's land. That is
  `exyliaprotections.bypass`.

## What bypass lets through

A player who bypasses passes every check inside a protection: blocks, containers, doors, entities, entry,
locks and bans. They also act in worlds whose protections have not finished loading after a restart, where
everybody else is told to wait.

The node only counts when it is *set* on the player, and since 1.0.2 it defaults to nobody: operators are
bound by protections like anybody else, so they can test their own land. Grant it to whoever must bypass:

```text
/lp user Notch permission set exyliaprotections.bypass true
```

<Callout type="note" title="Before 1.0.2">
`exyliaprotections.bypass` defaulted to `op`, and a default counts as set, so every operator bypassed every
protection out of the box.
</Callout>

## How many protections a player may own

| Permission | What it sets |
|---|---|
| `exyliaprotections.limit.<n>` | The player may own `n` protections. |

The highest number wins, and `exyliaprotections.limit.0` is a limit like any other: that player may own none.
A player with no limit node gets `settings.default-limit` from `config.yml` (3). A node whose end is not a
number is ignored.

Two more limits stack on top, from `config.yml`: `tiers.<id>.limit` caps how many of one tier a player may
own, and `settings.world-limits` caps how many they may own per world. See
[Creating protections](/docs/exyliaprotections/creating-protections).

## Permissions named in config.yml

| Where | What it gates | Default |
|---|---|---|
| `tiers.<id>.permission` | Placing a core of that tier, protecting land by selection when it is `selection.tier` (since 1.0.2), buying it from the shop and buying a protection of that tier on the market or receiving it by transfer. | Empty: anybody. |
| `upgrades.tiers.<tier>.levels.<n>.permission` | Upgrading to that level. | Empty: anybody. |

They can be any node, such as `rank.vip`.

## ExyliaSurvivalCore names

Since 1.0.2 the old `exyliasurvivalcore.protections*` nodes, and the `exyliasurvivalcore.protections.limit.<n>`
limits, are no longer declared or read. Grant the `exyliaprotections.*` names instead.

## Role permissions are not these

What a member may do inside one protection — `break`, `containers`, `manage-members`, `bank-withdraw` and
the rest — is a role permission, set per protection from its menu. They are not server permissions and no
permissions plugin grants them. See [People and access](/docs/exyliaprotections/people-and-access).

## Examples

Letting the VIP rank own six protections:

```text
/lp group vip permission set exyliaprotections.limit.6 true
```

Keeping new players off selections on a server that turned `selection.enabled` on:

```text
/lp group default permission set exyliaprotections.select false
```

Handing the admin menu to moderators who are not operators, without letting them build anywhere:

```text
/lp group moderator permission set exyliaprotections.admin true
```
