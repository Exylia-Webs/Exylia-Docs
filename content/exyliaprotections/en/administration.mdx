What only staff do: find any protection on the network and put it right, change settings, tiers, forced flags
and features without touching the file, and clear out land nobody plays in. Every menu and command on this page needs `exyliaprotections.admin`,
which operators have by default.

<Callout type="warning" title="Admin is not bypass">
`exyliaprotections.admin` counts as the owner of every protection in menus and commands, and lets its holder
enter every protection. It does not let them break, place or open anything inside one. That is
`exyliaprotections.bypass`, which nobody has by default, operators included, and which only counts when it is
**set** on the player. An admin breaking somebody's core is offered
to pick it up, like its owner. See [Permissions](/docs/exyliaprotections/permissions).
</Callout>

## The admin hub

`/protectionsadmin` (also `/psadmin`, `/padmin`, or the old `/protections admin`) opens the hub: a header with
how many protections and owners there are, the backend and this server's id, and one card per area.

| Card | Opens | Shows |
|---|---|---|
| Protections | The admin search below | Total protections |
| Tiers | The [tier editor](#the-tier-editor) | How many tiers |
| Forced flags | The `flags` settings | How many flags are forced |
| Features | The `features` settings | How many features are on, of all |
| General | The `general` settings | |
| Teleport | The `teleport` settings | |
| Cleanup | The [inactive cleanup](#inactive-cleanup) | |
| Reload | Runs `/protectionsadmin reload` | |

Every subcommand is listed on [Commands](/docs/exyliaprotections/commands#staff-commands).

## In-game settings

Each settings group lists its keys of `config.yml` with their current value. A click changes one and writes it
into `config.yml` on the spot, checked like a value typed into the file: one it does not take is refused with
the reason. The new value applies at once on this server; other servers reading the same file pick it up on
their next reload or restart.

| Group | Keys | How a click changes it |
|---|---|---|
| `general` | `settings.default-limit` (0–1000), `settings.min-distance` (0–512), `settings.disabled-worlds`, `settings.move-price`, `settings.deny-message-cooldown-millis` (0–60000), `settings.worldguard-priority` (−1000–1000), `cores.enabled`, `selection.enabled`, `selection.price-per-block`, `selection.min-side` (1–512), `selection.max-area` | Switches flip; numbers are typed within their range; `disabled-worlds` adds or removes the world you stand in |
| `teleport` | Every key of [`teleport`](/docs/exyliaprotections/configuration#teleport): `warmup-seconds` (0–60), `warp-warmup-seconds` (−1–60), `cancel-on-move`, `cancel-on-damage`, `refuse-in-combat`, `cooldown-seconds` (0–86400), `bypass-permission`, `tick-sound` | Texts are typed; `-` leaves one blank |
| `features` | Every switch of `submodules` | Click to turn it on or off |
| `flags` | One row per flag, under `forced-flags` | Each click: allowed → denied → each owner's choice |

Turning a feature or a forced flag on or off also updates the mirrored WorldGuard regions with the WORLDGUARD
backend. `/protectionsadmin flag` and `/protectionsadmin feature` do the same from the chat or the console. See
[Configuration](/docs/exyliaprotections/configuration#forced-flags) for what a forced flag does.

`/protectionsadmin reload` reads `config.yml`, the messages and the menus again, re-applies the backend to every
protection and restarts the upkeep, map and log timers.

## The admin search

The **Protections** card, or `/protectionsadmin list [owner]`, lists every protection on the network, sorted by owner and then by name. Left-click one to
open its admin screen; right-click teleports to it.

Five filters narrow the list. Left-click a filter to set it and right-click to clear it; right-click the
**Protection admin** button in the middle to clear them all.

| Filter | How it is set |
|---|---|
| Owner | Typed; any owner whose name contains it |
| Name | Typed; a protection whose name contains it, or whose id starts with it |
| World | Each click moves to the next world a protection is in, then back to any |
| Server | Each click moves to the next server, then back to any |
| State | Any → normal → raidable → abandoned → for sale → for rent → any |

A protection's state is the most urgent thing about it, in that order: raidable, abandoned, for sale, for rent
(it, or one of its plots, has a rent offer), normal. Each admin's filters are their own, and kept until they log
out. `/protectionsadmin list <owner>` sets the owner filter before opening.

The row of a protection shows its owner, tier, size, world, server, core location, members and state. The
**Tier editor** and **Inactive cleanup** buttons open the sections below.

## The admin screen of a protection

Opened from the search, or with `/protectionsadmin here` standing in the protection.

The top of the screen shows the owner, tier and level, state, size, members, bank, location, server, when its
owner or a member last played, and how long ago it was made.

| Button | What it does |
|---|---|
| Open as owner | Its own protection screen. An admin passes every owner and role check there |
| Teleport | To its home, or on top of its core without one, on any server, with the teleport countdown |
| Logs | Its audit log. With `submodules.logs` on |
| Set level | With upgrades on. From 0 to the tier's highest level. See below |
| Transfer | Type a player's name to hand it to them |
| Lives | With raids on. Left-click sets its lives; right-click clears its raid |
| Upkeep | With upkeep on. Forgives an abandonment |
| Force delete | Deletes it after a dangerous confirmation, whatever it is doing |

**Set level.** A higher level grows the land the way an upgrade does, by the difference in `radius-bonus`, and
is refused when the grown land would overlap another protection of that server and world. A lower level keeps
the land as it is; only the level and what it unlocks change. Nothing is charged.

<Callout type="note" title="Set level checks less than an upgrade">
Raising the level from the admin screen only checks for overlap. Unlike a player's upgrade it does not check
`settings.min-distance`, foreign WorldGuard regions, disabled worlds or the world border, and it works while
the protection is raidable, abandoned or rented.
</Callout>

**Transfer.** The player is found by name, online or not, and the protection is theirs, whatever their limits
or the tier's permission say. Everything else follows the rules of a sale: members stay or go as
`market.keep-members` says, rents end with each tenant paid back from the bank, and offers are withdrawn. See
[Economy](/docs/exyliaprotections/economy#what-changes-hands). It is not refused while the protection is
raidable, abandoned or rented.

**Lives.** Setting the lives asks for a number from 1 to the protection's maximum, ends any raid and cooldown,
and starts the regrowth clock from now. Clearing the raid gives every life back, with no raid and no cooldown.
See [Raids](/docs/exyliaprotections/raids).

**Upkeep.** Only for an abandoned protection: nothing is owed any more, the next period starts now, and the
owner counts as seen, so the next check does not abandon it again at once. It is refused while the bank is
busy. See [Economy](/docs/exyliaprotections/economy#abandoned).

**Force delete.** Deletes it even while it is raided, abandoned, rented or for sale. Tenants are paid back from
the bank first and the rest of the bank goes to the owner, as with any deleted protection. The core block is
removed and not given back.

`/protectionsadmin level`, `lives`, `transfer` and `delete` do the same as these buttons for the protection you
stand in.

Every change made here is written to the protection's log as done by an admin, and from the console as done by
the console.

## The staff log

Since 1.0.2 what an admin does to somebody's protection is also recorded in ExyliaLib's staff log, read with
`/exylialib logs`: who did it, the owner it was done to, and the protection's name, id and what changed.

| Action | When |
|---|---|
| `protection-lives` | Lives set |
| `protection-raid-clear` | Raid cleared |
| `protection-level` | Level set |
| `protection-transfer` | Handed to another player |
| `protection-delete` | Force deleted |
| `protection-cleanup` | Removed by the inactive cleanup |

Forgiving an abandonment and tier edits are not recorded there.

## The tier editor

**Tiers** in the hub, or `/protectionsadmin tiers`, lists every tier with its size, height, shop price, limit and how many protections on the
network use it. **New tier** asks for an id, up to 32 of `a-z`, `0-9`, `-` and `_`, and opens it with the
fields of a new tier: an `AMETHYST_BLOCK` core named `PROTECTION CORE`, no lore, radius 10, `FULL` height,
`y-radius` 10, not sold in the shop, no permission, no limit and no flags on.

| Button | Writes | Input |
|---|---|---|
| Core block | `material` | Put in an item; it must be a block |
| Name | `name` | Text, up to 256 characters; colour tokens and `&l` allowed |
| Lore | `lore` | Text, up to 2048 characters; lines split with `\|` |
| Radius | `radius` | 0 to 512 |
| Height | `height` | Click to switch between `FULL` and `CUBOID` |
| Cuboid height | `y-radius` | 0 to 512 |
| Shop price | `price` | 0 or more; 0 keeps it out of the shop |
| Currency | `currency` | Click to move to the next currency of the economy, then back to the default |
| Permission | `permission` | Text; `-` for none |
| Limit | `limit` | 0 to 1000; 0 for no limit of its own |
| Lives | `raids.tier-lives.<tier>` | 1 to 100 |
| Upkeep | `upkeep.tier-costs.<tier>` | 0 or more |
| Flags | `flags` | One switch per flag at the bottom, for the flags a new protection of this tier starts with |

Each change rewrites `config.yml` on the spot and applies at once, on this server. Other servers reading the same
file pick it up on their next reload or restart. A tier's lives and upkeep cost are kept in their own sections; a tier never
given them uses `raids.default-lives` and `upkeep.default-cost`. What every key means is on
[Creating protections](/docs/exyliaprotections/creating-protections).

**Delete tier** is refused while any protection on the network uses the tier, and for the tier `selection.tier`
names. After a dangerous confirmation the tier goes, with its lives and upkeep entries. Its core items stop
working: placing one is refused.

<Callout type="warning" title="A tier change does not reach existing protections">
Protections keep the box they were given; a new radius or height only applies to cores placed afterwards. The
same goes for the starting flags. Changing the core block is the one to be careful with: a core is only removed
from the world while it is still the tier's block, so deleting or picking up a protection placed with the old
block leaves that block standing.
</Callout>

## Inactive cleanup

Removes protections whose owner and members all stopped playing.

**From the menu.** **Cleanup** in the hub, or **Inactive cleanup** in the search, asks how many days, 1 to 3650, offering `cleanup.default-days` first,
and opens the preview: every protection that would go, oldest first, with how long ago its players were last
seen. Clicking one opens its admin screen.

| Button | What it does |
|---|---|
| Never seen players | Switches whether protections with a player who was never seen are removed too |
| Days | Asks for other days |
| Remove | After a dangerous confirmation naming how many, removes them |

**From the command.** `/protectionsadmin cleanup <days>` prints how many would go, how many were kept for
having a never-seen player, a tenant or money in the bank, and the first ten with their world and server.
Adding `confirm` runs it at once, with no further question. Days below 1 count as 1.

A protection is removed when:

1. Its owner and every player member were last seen more than that many days ago. Clan members do not count:
   a clan is added whole.
2. Nobody in it is **unknown**, never seen, unless `--include-unknown`, or the menu's **Never seen players**
   switch, is on.
3. Nobody rents in it right now, with `cleanup.skip-with-tenants`.
4. Its bank holds nothing, with `cleanup.skip-with-bank`.

"Last seen" is a player's last join or quit on any server of the network, and now while they are online on this
server. The plan is made again when the removal starts, and each protection is judged once more just before it
goes, so an owner who came back since the preview keeps their land. Removal runs `batch-size` protections a tick
and tells whoever started it how many it removed. Each one is logged as removed by the inactivity cleanup, its
bank goes to the owner, and its core block is removed.

| Key | Default | What it does |
|---|---|---|
| `cleanup.default-days` | `30` | Days the menu asks about first |
| `cleanup.skip-with-tenants` | `true` | Keep protections with a tenant renting in them right now |
| `cleanup.skip-with-bank` | `false` | Keep protections whose bank holds money. Off: the money is paid to the owner |
| `cleanup.batch-size` | `20` | Protections removed per tick while a cleanup runs |

<Callout type="note" title="Nobody is inactive before the plugin has watched them">
When protections load, every owner and member with no last-seen record is recorded as seen at that moment. On a
server that just started using the plugin nothing is removed until that many days have passed, and "unknown"
only covers players added since the last start who have not joined since.
</Callout>

A cleanup still running when the server stops is cancelled; what it had not removed yet stays.

## All keys

```yaml title="plugins/ExyliaProtections/config.yml"
cleanup:
  default-days: 30
  skip-with-tenants: true
  skip-with-bank: false
  batch-size: 20
```
