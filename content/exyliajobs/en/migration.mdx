At the end of this page your jobs and your players' levels from the old plugin are in ExyliaJobs. Preview first: the preview writes nothing, and running the import twice never adds levels up.

## Before you start

Keep the old plugin's folder in `plugins/` (`plugins/Jobs`, `plugins/eco`, `plugins/ExcellentJobs` or `plugins/AdvancedJobs`): the import reads it. The old plugin may stay installed while you import; afterwards you are reminded to remove it. Supported sources are `jobsreborn`, `ecojobs`, `excellentjobs` and `advancedjobs`. You need `exyliajobs.admin`.

## Steps

<Steps>
  <Step title="Open Migration">
    Run `/jobsadmin` and click **Migration**, then click your old plugin (**Import ▸ Jobs Reborn**, **EcoJobs**, **ExcellentJobs** or **AdvancedJobs**). Or run `/jobsadmin import <source>`.
  </Step>
  <Step title="Read the preview">
    The preview screen shows the players and standings found, the jobs that are new and merged, the old jobs with no match, and every entry of the old files that has no place here. It is read off the main thread and writes nothing. In the console, `/jobsadmin import <source> -dry` prints the same.
  </Step>
  <Step title="Import">
    Click **Preview ▸ Import** and confirm in game. In the console run `/jobsadmin import <source> -confirm`.
  </Step>
  <Step title="Remove the old plugin">
    Take the old plugin out of `plugins/` and restart, so two plugins do not pay for the same action.
  </Step>
</Steps>

## Check that it works

Run `/jobsadmin`, click **Editor**: the imported jobs are listed. Ask a player with progress to run `/jobs`: their level and experience match the old plugin's. Run the import again: nothing changes.

## Going further

### What each source gives

| Source | Folder read | Imports |
|---|---|---|
| Jobs Reborn | `plugins/Jobs` | Job files (`jobs/*.yml`, or the old `jobConfig.yml`) and levels, from SQLite (`jobs.sqlite.db`) or MySQL (`generalConfig.yml`, table prefix honoured). |
| EcoJobs | `plugins/eco` | Levels, joined jobs and experience from eco's `data.yml`, SQLite or MySQL/MariaDB (and the legacy `eco_data` table). |
| ExcellentJobs | `plugins/ExcellentJobs` | Levels, from SQLite or MySQL (`job_data` and the older JSON `data` column). |
| AdvancedJobs | `plugins/AdvancedJobs` | Levels only, **unverified**: the plugin is closed source, so tables and YAML player files are read by guessing column and key names. MySQL is not read. |

<Callout type="warning" title="Not supported">
EcoJobs data kept in MongoDB, PostgreSQL or Redis is not read: the console says so. Switch eco's `data-handler` to `sqlite` or `mysql` (eco moves the data) and import again.
</Callout>

### How levels and jobs are matched

- A new job file is written as it is. A job that already has a file here is **merged**: only targets yours lacks are added and the old file is copied to `imports/backup/` first.
- Standings match jobs by id, a name synonym (fisherman, lumberjack, excavator, blacksmith, alchemist, breeder, fighter...) or the display name; the rest are listed as unmatched.
- Levels **never add up**: a standing is written only when higher (level, then experience) than what the player has here, so running it twice changes nothing. Online players are updated in memory. Imported jobs held there are joined here.
- It is logged in the audit log as `jobs-import`.

<Details title="How Jobs Reborn files convert">

Actions map to `break`, `strip-log`, `place`, `kill` (also `mmkill`, as `mythicmobs:<id>`), `fish`, `craft`, `villager-trade`, `smelt`, `brew`, `enchant`, `repair`, `breed`, `tame`, `shear`, `milk`, `explore`, `eat` and `collect`. The level equation becomes a `formula` curve when readable (else the default curve). Names are made plain and old item names updated.

Not carried, and listed in the preview and in the new file's header: points, negative pay, `from-level`/`until-level`, sub-types (pay applies to any), items matched by display name, enchantment targets, exploring past the first player, and actions such as `tntbreak`, `dye` or custom fishing plugins.
</Details>
